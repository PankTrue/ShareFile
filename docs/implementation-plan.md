# ShareFile: отдельные этапы реализации

Основание: [требования и технический проект](architecture.md). План подтверждён пользователем. Backend и React Web UI реализованы и проверяются локально; desktop-этапы 3–6 пока не начаты. Инструкция этапа 7 подготовлена, устройство ещё не проверено. Оценок сроков нет.

Этапы имеют отдельные сборки и проверяемый результат в одном репозитории. Для API сначала фиксируется контракт, затем Web UI и клиенты используют его независимо. Рекомендуемый старт — backend. Подзадачи backend не требуют разработки интерфейсов остальных этапов.

## 1. Backend на Go

Статус: реализован. API/CLI, конфигурация и инструкция Entware готовы; результаты локальной приёмки — [validation.md](validation.md). На устройстве не развёрнут. Пакет supervision подготовлен, фактические Entware/Cloud проверки относятся к этапу 7.

Результат: серверный API с SQLite-метаданными, файлами на HDD и сборкой Linux ARM64 без cgo.

Последовательные подзадачи:

1. Основа проекта и контракт API: `cmd`/`internal`, конфигурация, жизненный цикл HTTP, OpenAPI, versioned migrations и проверка корня хранения.
2. Идентификация: начальный администратор через CLI, пользователи, группы, пароли, browser-сессии, подключение и отзыв устройств.
3. Дерево и права: личные/общие папки, наследуемые роли, пагинация, переименование и перемещение, проверка разрешений всех операций.
4. Передача: resumable upload, публикация завершённого объекта, HTTP Range, отмена и истечение сессий, восстановление после падения и недоступного HDD.
5. Жизненный цикл: разрешение совпадений имён, явная замена, корзина, восстановление, очистка и импорт-копирование.
6. Ссылки: ссылки на файлы и папки, пароли, сроки, отзыв и необратимое отключение при потере оснований доступа.
7. Изоляция и эксплуатация: публичный/приватный listener, настройка TLS, health, ограниченные логи, процедуры backup/restore и release-сборка.

Приёмка: интеграционные проверки API, SQL и реального временного хранения; воспроизводимые обрыв/возобновление и восстановление; проверка приватных административных маршрутов; успешная ARM64-сборка. Работа на роутере подтверждается отдельно этапом 7.

## 2. Web UI

Статус: реализован на React + TypeScript + Vite. Исходники и самостоятельная сборка — `web/`, запуск и проверки — [web-ui.md](web-ui.md).

Результат: независимо собираемый статический интерфейс, обслуживаемый Go-сервером.

Пользовательский интерфейс включает вход, папки, загрузки с прогрессом и возобновлением, управление файлами, корзину, ссылки и подключённые устройства. Административный интерфейс включает пользователей, группы, назначения прав, импорт и настройки; он работает через приватный listener.

Приёмка: полный сценарий через браузер, видимость функций по текущим правам, корректные ошибки передачи/заполнения диска и отсутствие административных операций на публичном origin.

## 3. Общее ядро desktop-клиентов

Результат: Go-модуль и утилита для повторно используемой логики API, resumable transfer, очереди, прогресса, создания ссылок и подключения устройства через браузер.

Интерфейс ядра описывает подключение, отмену/продолжение, статусы и результат; платформенные adapters отвечают за UI, контекстное меню, системное хранение токена и буфер обмена.

Приёмка: один сценарий загрузки и создания ссылки работает с backend; потеря соединения и повтор после рестарта клиента не создают дубли; отзыв устройства прекращает его авторизованные операции.

## 4. Клиент macOS

Результат: небольшая утилита и Finder Quick Action/Service «Загрузить и поделиться», настройки и прогресс, системное хранение токена, копирование ссылок и установщик.

Зависит от этапа 3 и согласованной версии API. Приёмка: выбранные файлы, включая имена с пробелами и Unicode, передаются корректно; отказ пользователя в доступе к файлам отображается; длительная загрузка не блокирует Finder. В релизе фиксируются поддерживаемые macOS и архитектуры.

## 5. Клиент Linux

Результат: небольшая утилита, отдельные интеграции Nautilus и Dolphin, настройки/прогресс, системное хранение токена, буфер обмена и процедура установки/удаления.

Зависит от этапа 3 и согласованной версии API. Приёмка: одинаковый upload/share-сценарий в обоих файловых менеджерах; корректная обработка нескольких локальных файлов и отсутствующего credential store. В релизе фиксируются проверенные дистрибутивы, desktop-версии и архитектуры.

## 6. Клиент Windows

Результат: небольшая утилита, пункт Explorer через «Показать дополнительные параметры», настройки/прогресс, системное хранение токена, буфер обмена и установщик.

Зависит от этапа 3 и согласованной версии API. Приёмка: один/несколько файлов, пробелы и Unicode в путях, возобновление после обрыва, отзыв устройства и удаление регистрации меню вместе с приложением. В релизе фиксируются проверенные версии Windows и архитектуры.

## 7. Развёртывание и проверка Keenetic

Результат: пакет для Entware, инструкции установки, автозапуска, supervision, обновления и отката; схема KeenDNS; подтверждение поведения на KN-1811.

Сначала read-only проверяются IP/режим KeenDNS, KeeneticOS, ядро, HDD и его файловая система. Устройство, его конфигурация и данные на диске не меняются в рамках самого интервью.

Приёмка: рестарт и восстановление загрузки, большой файл и контрольная сумма из внешней сети, HTTP Range, приватная админка только из LAN/VPN, измерения памяти/CPU и воспроизводимый backup/restore. Для Cloud отдельно проверяется прохождение протокола возобновления и длительных передач. Фактическое развёртывание требует подключения к устройству и подготовленной конфигурации.

## Последующие расширения

Отдельно от перечисленных этапов: история версий; исключения ACL для файлов и разрыв наследования; обязательная 2FA; desktop-файловый менеджер; загрузка деревьев папок и архивное скачивание; современное основное меню Windows; другие Linux-файловые менеджеры; автоматические внешние резервные копии.
